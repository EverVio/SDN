# 遇到的问题

## 环节 2：Mininet 拓扑 — 广播风暴导致 83% 丢包

### 现象

使用 `simple_switch_13` 控制器启动双路径拓扑后，执行 `pingall` 结果为 83% dropped（2/12 received）。只有连接在同一交换机 s1 上的 h1 和 h2 能互通，h3、h4 与 h1、h2 之间完全不通。

```
mininet> pingall
*** Ping: testing ping reachability
h1 -> h2 X X
h2 -> h1 X X
h3 -> X X X
h4 -> X X X
*** Results: 83% dropped (2/12 received)
```

### 根本原因：双路径拓扑存在物理环路

拓扑结构包含环路 `s1 → s2 → s4 → s3 → s1`。`simple_switch_13` 是一个基础的 base 学习交换机，遇到未知目的 MAC 时会向除入端口外的所有端口泛洪（FLOOD）。在环路拓扑中，泛洪的数据包会无限复制，形成广播风暴。

风暴形成过程：
1. h1 ping h3，首先发出 ARP 请求（广播包）
2. s1 收到 ARP，不知道 h3 在哪，泛洪到 s2 和 s3
3. s2 收到后泛洪给 s4，s3 收到后也泛洪给 s4
4. s4 从 s2 和 s3 分别收到同一份 ARP 包，继续泛洪：把从 s2 收到的发给 s3，从 s3 收到的发给 s2
5. 这些包沿原路返回 s1，s1 继续泛洪……数据包在网络中呈指数级复制

### 日志证据

**证据一：控制器被海量 Packet-In 淹没**

`dump-flows s1` 中 `priority=0` 的 table-miss 规则计数：

```
cookie=0x0, duration=108.599s, table=0, n_packets=166203, n_bytes=14000838,
priority=0 actions=CONTROLLER:65535
```

在 ~108 秒内，s1 产生了超过 16 万个未匹配的包被送往控制器，导致控制平面 CPU 满载。

**证据二：MAC 地址震荡（MAC Flapping）**

```
cookie=0x0, duration=91.394s, table=0, n_packets=1006, n_bytes=42308,
priority=1,in_port="s1-eth4",dl_src=00:00:00:00:00:04,dl_dst=00:00:00:00:00:01
actions=output:"s1-eth4"
```

从 s1-eth4 进来的包，动作是从 s1-eth4 发出去——这是完全错误的逻辑。数据包在环路中不断绕圈，控制器一会在 eth3 看到 h4 的源 MAC，一会在 eth4 看到，导致 MAC 学习表不断被错误覆写。

**证据三：只有同交换机主机能通**

h1 和 h2 都挂在 s1 上，ARP 交互不需要经过引发环路的核心链路（s1-s2-s4-s3），所以它们之间能正常通信。

### 解决方案

使用 Ryu 自带的支持 STP（生成树协议）的控制器：

```bash
# 清理残留网络状态（风暴发生后环境已被污染）
sudo mn -c

# 启动 STP 控制器
ryu-manager ryu.app.simple_switch_stp_13
```

然后重新启动拓扑脚本。STP 会自动检测环路，在逻辑上阻塞一条路径（如 s3-s4 链路）来打破环路。STP 选举需要约 15-30 秒，启动后等待再执行 `pingall`。

### 修复后验证

```
mininet> pingall
*** Ping: testing ping reachability
h1 -> h2 h3 h4
h2 -> h1 h3 h4
h3 -> h1 h2 h4
h4 -> h1 h2 h3
*** Results: 0% dropped (12/12 received)
```

iperf 吞吐量测试也正常：

```
mininet> h1 iperf -s &
mininet> h3 iperf -c 10.0.0.1 -t 5
[ ID] Interval       Transfer     Bandwidth
[  1] 0.0000-5.3171 sec  6.00 MBytes  9.47 Mbits/sec
```

### 对后续开发的启示

STP 会阻塞一条链路，意味着无法同时利用两条路径进行负载均衡。在后续编写 `load_balancer.py` 时，需要抛弃基础控制器中盲目 `OFPP_FLOOD` 的做法，改为：
- 利用 Ryu 的 topology API 自动发现网络拓扑
- 对 ARP 等广播包进行特殊处理（如控制器代为响应，或仅在一条路径上转发）
- 通过明确指定路由来避免数据包在环路中无限转发

## 环节 3：基础控制器 pingall 100% 丢包 — 缺少 IPv6 过滤、MAC 锁定与 ARP 风暴抑制

### 现象

按照计划文档中的代码实现 `base_controller.py`（仅过滤 LLDP、MAC 学习时无条件覆写），使用 `simple_switch_stp_13` 的 STP 机制已解决广播风暴问题，但自定义控制器运行 `pingall` 时仍然 100% 丢包：

```
mininet> pingall
*** Ping: testing ping reachability
h1 -> X X X
h2 -> X X X
h3 -> X X X
h4 -> X X X
*** Results: 100% dropped (0/12 received)
```

加入 IPv6 过滤和 MAC 锁定后，`pingall` 可以 0% 丢包通过，但存在隐蔽的 ARP 风暴问题：`pingall` 结束后静置几秒，查看 `sh ovs-ofctl dump-flows s1 -O OpenFlow13`，会发现 `priority=0` 的 table-miss 规则的 `n_packets` 仍在疯狂增长。单播数据包（ICMP）走的是已安装的流表规则（优先级 1），不受影响；但 ARP 广播包走的是 table-miss 规则（优先级 0），在环路中持续泛洪，挤占核心链路带宽和控制器处理能力。

### 根本原因

三个问题叠加导致全部失败：

**原因一：IPv6 组播包未过滤**

Mininet 中的主机在初始化时会自动发送 IPv6 组播包（如邻居发现 ND、组播侦听 MLD）。这些包的 ethertype 为 `0x86DD`。如果控制器不主动过滤，它们会触发大量 Packet-In，和 LLDP 包一起淹没控制器。在环路拓扑中，这些广播包还会在交换机之间反复泛洪，进一步加剧问题。即使有 STP 阻塞一条路径，大量 IPv6 包仍然会严重拖慢控制器处理速度，导致正常的 ARP 和 ICMP 包无法被及时处理。

**原因二：MAC 地址端口映射漂移（MAC Flapping）**

原始代码对每个 Packet-In 都无条件更新 MAC 表：

```python
# 原始代码 — 有 bug
self.mac_to_port[dpid][src] = in_port
```

在环路拓扑中，即使 STP 阻塞了一条链路，泛洪的 ARP 包仍可能从非预期端口回到交换机。例如：
1. h1 的 ARP 请求从 s1 的 port1 进入，控制器学习到 `h1_mac → port1`
2. ARP 经过路径 A 到达 s4，s4 泛洪后 ARP 可能沿路径 B 的残留链路传回 s1
3. s1 从 port4 收到同一个 ARP，控制器错误地将 h1 的 MAC 更新为 `port4`
4. 后续发往 h1 的包从 port4 出去，永远到不了 h1

**原因三：广播包在环路中持续泛洪**

即使解决了 MAC Flapping，广播包仍然会在环路中不断泛洪。单播数据包（ICMP ping）走的是已安装的流表规则（优先级 1），看起来正常工作；但广播包走的是 table-miss 规则（优先级 0），匹配后被发往控制器。在环路拓扑中，这些广播包会从多条路径反复到达同一交换机，导致 `priority=0` 规则的 `n_packets` 疯狂增长。虽然 ICMP 本身不受影响，但控制器和核心链路一直在被无用的广播包消耗资源，`pingall` 测试也会被严重拖慢。

需要特别注意：OpenFlow 的 `OFPP_FLOOD` 动作不仅应用于广播包（`dst=ff:ff:ff:ff:ff:ff`），还会应用于未知单播（Unknown Unicast）。如果仅拦截 ARP，当网络中出现目的 MAC 未知的单播数据包时，该包同样会在环路中无限循环。因此抑制范围必须覆盖所有广播包。

### 解决方案

在 `packet_in_handler` 中加入三处关键修改：

**修改一：同时过滤 IPv6 和 LLDP**

```python
# 原始代码 — 只过滤 LLDP
if eth.ethertype == ether_types.ETH_TYPE_LLDP:
    return

# 修改后 — 同时过滤 IPv6 和 LLDP
if eth.ethertype in (ether_types.ETH_TYPE_LLDP, ether_types.ETH_TYPE_IPV6):
    return
```

**修改二：MAC 地址锁定（只学一次）**

```python
# 原始代码 — 每次都覆写，会导致 MAC Flapping
self.mac_to_port[dpid][src] = in_port

# 修改后 — 只在首次见到时学习，之后锁定
if src not in self.mac_to_port[dpid]:
    self.mac_to_port[dpid][src] = in_port
    self.logger.info("Switch %s: learn %s on port %d", dpid, src, in_port)
```

**修改三：广播风暴抑制（时间窗去重 + 内存泄漏防护）**

```python
# 在 __init__ 中添加
self.broadcast_cache = {}  # {(dpid, src_mac, eth_type): timestamp}
self.cache_limit = 1000    # 缓存最大容量，防止内存泄漏

# 在 packet_in_handler 中，IPv6 过滤之后、MAC 学习之前添加
# 拦截所有目标 MAC 为全 F 的广播包（包含 ARP、RARP 等）
if dst == 'ff:ff:ff:ff:ff:ff':
    cache_key = (dpid, src, eth.ethertype)
    now = time.time()
    # 定期清理缓存，防止内存泄漏
    if len(self.broadcast_cache) > self.cache_limit:
        self.broadcast_cache.clear()
    if cache_key in self.broadcast_cache:
        if now - self.broadcast_cache[cache_key] < 0.5:
            return  # 0.5 秒内重复广播包，判定为环路包，丢弃
    self.broadcast_cache[cache_key] = now
```

### 修复后验证

```
mininet> pingall
*** Ping: testing ping reachability
h1 -> h2 h3 h4
h2 -> h1 h3 h4
h3 -> h1 h2 h4
h4 -> h1 h2 h3
*** Results: 0% dropped (12/12 received)
```

验证广播风暴抑制是否生效：`pingall` 结束后静置几秒钟，然后查看流表：

```bash
mininet> sh ovs-ofctl dump-flows s1 -O OpenFlow13
```

观察 `priority=0` 的 table-miss 规则的 `n_packets` 字段。如果广播风暴抑制正常工作，该数值应该保持在较低水平（数百到数千），而非疯狂增长到数万甚至数十万。

### 为什么当前实现"看似"有效

三个条件叠加后，`pingall` 能 0% 丢包通过，但需要理解每个条件的作用机制：

1. **IPv6 过滤**消除了 Mininet 主机初始化时的组播噪声，减少了控制器的无效处理负担。
2. **MAC 锁定**防止了环路传回的包导致端口映射漂移。广播丢弃逻辑放在 MAC 学习之前，当环路传回重复的广播包时，控制器直接 return，交换机不会在不同端口上来回学习同一个源 MAC 地址。
3. **广播抑制**的 0.5 秒时间窗阻断了双路径拓扑中由环路引发的瞬时广播风暴，使 `n_packets` 保持在合理水平。

### 已知局限与正确的工程实践

当前实现存在三个核心缺陷：

1. **无法防御未知单播风暴：** 当前逻辑只拦截了广播包（`dst=ff:ff:ff:ff:ff:ff`）。但 OpenFlow 的 `OFPP_FLOOD` 动作还会应用于未知单播——如果交换机尚未学习到目的 MAC，单播包同样会在环路中无限循环。当前代码对此无能为力。
2. **内存泄漏风险：** `broadcast_cache` 是只增不减的字典（仅在超限时清空）。如果清空时机不当或 `cache_limit` 设置过大，长期运行仍可能 OOM。
3. **误杀合法重传：** 如果主机的网络协议栈因拥塞在 0.5 秒内合法重传了相同的广播请求，该机制会将其误判为环路包并丢弃。

**正确的工程实践：** 在真正的二层网络中，解决环路的唯一正规方法是引入生成树协议（STP / RSTP）来逻辑阻塞冗余链路，而不是靠控制器去猜和丢包。Ryu 官方提供了自带 STP 功能的组件（`ryu.app.simple_switch_stp_13`）。本控制器的广播抑制是在 STP 收敛期间（15-30 秒）的临时防护，不能替代 STP。

### 为什么计划文档中没有提到这三点？

计划文档中的 `base_controller.py` 代码是基于理想环境（无环路）编写的。在无环路拓扑中：
- IPv6 包虽多但不会环路放大，不会致命
- MAC 学习不会被环路包污染，因为包不会从非预期端口回来
- ARP 请求只会被泛洪一次，不会在环路中反复复制

但在实际的双路径拓扑中，即使有 STP 阻塞一条链路，环路的影响仍然存在（STP 收敛期间、BPDU 包的特殊处理等），这三处防护是必不可少的。

特别地，广播风暴抑制解决的是一个隐蔽问题：单播数据包（ICMP ping）走的是已安装的流表规则（优先级 1），看起来正常工作；但广播包走的是 table-miss 规则（优先级 0），会在环路中持续泛洪，导致 `n_packets` 疯狂增长。如果不检查流表计数器，很容易以为"pingall 通过了就没问题"，实际上控制器和链路一直在被无用的广播包消耗资源。

## 环节 3+5：数据采集依赖反转 — base_controller 无法生成双路径训练数据

### 现象

按照原计划的开发顺序：Phase 3（数据采集）→ Phase 4（ML 训练）→ Phase 5（阈值控制器）。使用 base_controller.py（base 学习交换机）作为控制器采集训练数据时，发现 `data/traffic_data.csv` 中只有 path_B 有非零利用率，path_A 的利用率始终为 0。

```
# 数据分布统计
link_label    count    mean     min     max
path_A        40       0.000    0.000   0.000
path_B        40       0.712    0.237   0.985
```

### 根本原因：base 学习交换机无法控制路径选择

base_controller.py 是一个标准的 base 学习交换机，数据包走哪条路径完全由 MAC 地址学习顺序决定。当 h1 第一次发包给 h3 时，s1 通过泛洪发现 h3 在 s4 上。由于双路径拓扑存在物理环路，泛洪的包会同时从 path_A（s1→s2→s4）和 path_B（s1→s3→s4）到达 s4。s4 最先从哪条路径收到包是随机的，但一旦学习到 h1 的 MAC 对应某个端口，后续所有包就固定走那条路径。

实测中，s4 先从 s3（path_B）收到 h1 的包，于是所有 h1→h3 的流量都走了 path_B，path_A 完全空闲。

### 对 ML 训练的致命影响

如果用这种单路径数据训练模型：
- path_A 的训练标签全为 0，模型学到 "path_A 永远空闲"
- path_B 的训练标签有正常波动，模型只学到 path_B 的规律
- 模型无法感知"两条路径同时有负载"的状态，更无法预测路径切换时机
- 上线后，当 AI 控制器将流量从 A 切到 B 时，模型对 path_B 的预测完全失效

### 解决方案：先实现 threshold_balancer.py，再采集数据

threshold_balancer.py 通过显式路径安装（在 s1、s2/s3、s4 所有交换机上预装流表）精确控制数据包走哪条路径。当 path_A 利用率超过 70% 时，控制器删除旧流表、安装新流表，将流量切换到 path_B。用它采集的数据天然包含两条路径的负载交替模式。

```
# 使用 threshold_balancer 采集的数据分布
link_label    count    mean     min     max
path_A        40       0.138    0.000   0.952
path_B        40       0.208    0.000   0.776
```

两条路径都有非零利用率，且能看到明显的路径切换时间点。

### 开发顺序调整

原计划的依赖链存在"鸡生蛋"问题：
- Phase 4（ML 训练）需要双路径训练数据
- 双路径训练数据需要 threshold_balancer.py
- threshold_balancer.py 原本排在 Phase 5（Phase 4 之后）

实际开发顺序应为：
1. Phase 3：StatsMixin + 流量生成器 + **threshold_balancer.py**
2. 使用 threshold_balancer 采集双路径训练数据
3. Phase 3 续：特征组装 + 模型训练
4. Phase 4：predictive_balancer.py（使用训练好的模型）
5. Phase 5：三阶段对照实验

已将原 Phase 3 和 Phase 5 合并为新的 Phase 3（基础设施与数据基础），原 Phase 4（ML 训练）降为 Phase 3 的子节，原 Phase 6 和 Phase 7 分别重编号为 Phase 4 和 Phase 5。

### 关键教训

**ML 训练数据的质量决定了模型的上限。** 在规划 ML 项目时，必须先确认数据采集环境能产生符合训练需求的数据。如果数据本身存在偏差（如单路径、单模式），再精巧的特征工程和模型架构也无法弥补。

在 SDN 场景中，"能采集数据"和"能采集到**有用的**数据"是两个完全不同的问题。base 学习交换机能采集数据，但数据质量不足以训练双路径预测模型。显式路径控制是获取高质量训练数据的前提条件。
