# 遇到的问题

## 环节 2：Mininet 拓扑 — 广播风暴导致 83% 丢包

### 现象

使用 `simple_switch_13` 控制器启动双路径拓扑后，执行 `pingall` 结果为 83% dropped（2/12 received）。只有连接在同一交换机 s1 上的 h1 和 h2 能互通，h3、h4 与 h1、h2 之间完全不通。

```
mininet> pingall
*** Ping: testing ping reachability
h1 -> h2 X X
h2 -> h1 X X
h3 -> X X X
h4 -> X X X
*** Results: 83% dropped (2/12 received)
```

### 根本原因：双路径拓扑存在物理环路

拓扑结构包含环路 `s1 → s2 → s4 → s3 → s1`。`simple_switch_13` 是一个基础的 L2 学习交换机，遇到未知目的 MAC 时会向除入端口外的所有端口泛洪（FLOOD）。在环路拓扑中，泛洪的数据包会无限复制，形成广播风暴。

风暴形成过程：
1. h1 ping h3，首先发出 ARP 请求（广播包）
2. s1 收到 ARP，不知道 h3 在哪，泛洪到 s2 和 s3
3. s2 收到后泛洪给 s4，s3 收到后也泛洪给 s4
4. s4 从 s2 和 s3 分别收到同一份 ARP 包，继续泛洪：把从 s2 收到的发给 s3，从 s3 收到的发给 s2
5. 这些包沿原路返回 s1，s1 继续泛洪……数据包在网络中呈指数级复制

### 日志证据

**证据一：控制器被海量 Packet-In 淹没**

`dump-flows s1` 中 `priority=0` 的 table-miss 规则计数：

```
cookie=0x0, duration=108.599s, table=0, n_packets=166203, n_bytes=14000838,
priority=0 actions=CONTROLLER:65535
```

在 ~108 秒内，s1 产生了超过 16 万个未匹配的包被送往控制器，导致控制平面 CPU 满载。

**证据二：MAC 地址震荡（MAC Flapping）**

```
cookie=0x0, duration=91.394s, table=0, n_packets=1006, n_bytes=42308,
priority=1,in_port="s1-eth4",dl_src=00:00:00:00:00:04,dl_dst=00:00:00:00:00:01
actions=output:"s1-eth4"
```

从 s1-eth4 进来的包，动作是从 s1-eth4 发出去——这是完全错误的逻辑。数据包在环路中不断绕圈，控制器一会在 eth3 看到 h4 的源 MAC，一会在 eth4 看到，导致 MAC 学习表不断被错误覆写。

**证据三：只有同交换机主机能通**

h1 和 h2 都挂在 s1 上，ARP 交互不需要经过引发环路的核心链路（s1-s2-s4-s3），所以它们之间能正常通信。

### 解决方案

使用 Ryu 自带的支持 STP（生成树协议）的控制器：

```bash
# 清理残留网络状态（风暴发生后环境已被污染）
sudo mn -c

# 启动 STP 控制器
ryu-manager ryu.app.simple_switch_stp_13
```

然后重新启动拓扑脚本。STP 会自动检测环路，在逻辑上阻塞一条路径（如 s3-s4 链路）来打破环路。STP 选举需要约 15-30 秒，启动后等待再执行 `pingall`。

### 修复后验证

```
mininet> pingall
*** Ping: testing ping reachability
h1 -> h2 h3 h4
h2 -> h1 h3 h4
h3 -> h1 h2 h4
h4 -> h1 h2 h3
*** Results: 0% dropped (12/12 received)
```

iperf 吞吐量测试也正常：

```
mininet> h1 iperf -s &
mininet> h3 iperf -c 10.0.0.1 -t 5
[ ID] Interval       Transfer     Bandwidth
[  1] 0.0000-5.3171 sec  6.00 MBytes  9.47 Mbits/sec
```

### 对后续开发的启示

STP 会阻塞一条链路，意味着无法同时利用两条路径进行负载均衡。在后续编写 `load_balancer.py` 时，需要抛弃基础控制器中盲目 `OFPP_FLOOD` 的做法，改为：
- 利用 Ryu 的 topology API 自动发现网络拓扑
- 对 ARP 等广播包进行特殊处理（如控制器代为响应，或仅在一条路径上转发）
- 通过明确指定路由来避免数据包在环路中无限转发
